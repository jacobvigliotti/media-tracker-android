## Part 2 — A Specific Bug

**2a. Describe the hardest bug you fixed this semester. Not the most recent one — the one that took the longest or cost you the most confusion. What was the symptom? What did you think the problem was at first? What was it actually? How did you find it?**

> Your answer: 
> 
> I struggled to get my access token to pass to the MediaDetailViewModel class. At first, I assumed the issue was with the credentials or the API itself, maybe the token wasn’t being generated correctly or the server wasn’t returning what I expected. After spending too much time chasing logs and other various debugging, I realized the problem wasn’t the API at all. The ViewModel needed an application context so it could work with my DefaultSessionRepository, which is what actually stores and retrieves the token.
>
> I found this by closely comparing how this screen differed from the SearchResultsViewModel, which similarly needed an authenticated token to pass its request to the API. Once I updated the class definition to accept an application context, everything started working. It was a great reminder that sometimes the bug isn’t where you think it is.

---

**2b. Copy and paste the specific lines of code you changed to fix it. (This can be a before/after comparison, a diff, or just the relevant snippet.) Explain in plain English what the fix does and why it works.**

> Your answer (include code):
> 
> The diff went from:
> 
> ```class MediaDetailViewModel : ViewModel() {```
> 
> To:
> 
> ```class MediaDetailViewModel(application: Application) : AndroidViewModel(application) {```

A simple change with a huge difference. I learned switching to AndroidViewModel gives the ViewModel access to the application context, which is required for the DefaultSessionRepository to retrieve the stored access token. Without that context, the repository behaves like no token exists, which breaks authenticated API calls. With the context, everything started working as expected.

## Part 3 — What You Actually Learned

**3a. Pick the concept from this semester that took the longest to actually understand — not just to implement, but to understand. Describe what you thought it was before you understood it, what changed, and how you would explain it now to a student who was exactly where you were at the start of the semester.**

> Your answer:
> 
> The longest concept to understand was how Compose handles state and recomposition. I initially thought mobile apps were built like websites, you create a static layout and then modify it with scripts. Through my experiences in the course I learned Compose works very differently and it’s based on the ability to completely recompose screens based on changes in state. 
> 
> Seeing how mutableStateOf creates observable values and how recomposition triggers UI updates helped everything click. Using remember to preserve values across recompositions reinforced the idea that Compose is always rebuilding the UI. If I were explaining this to a student, I’d tell them to imagine a website where every time the user interacts with something, the browser replaces the entire HTML element with a new one, but it keeps the parts you marked as “remembered.”
